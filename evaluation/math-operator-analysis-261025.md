# 수식 연산어 정규화와 CPU8 실행 검증

2026-10-25. **현재 서버를 8 CPU로 적용했고, 기존 반환 실패를 정규화로 해결했다.** 실제 212.6초 영상 API 시험에서는 4 CPU 133.98초·8 CPU 110.26초였고 두 조건 모두 17개 번역이 반환됐다. 이는 개발 영상의 관측 결과이며 모든 입력의 실패 0이나 일반 의미 정확도를 보장하는 수치가 아니다.

## 변경 내용

- `translation_normalization.py`는 원문에서 연산과 피연산자 쌍을 확인한 수식의 영어 연산어만 기호로 치환한다. 실제 실패의 `v0 plus u times ln(mR / 2m0)`는 **`v0 + u × ln(mR / 2m0)`**로 정리한다.
- `u ln`처럼 원문에 단일 항과 ln이 나란히 있는 경우에만 그 사이 times를 암묵 곱으로 허용한다. 출력에는 이미 완성된 지원 ln 괄호식이 있어야 한다. 계산·괄호 추가·로그 범위 추론·원문 수식 수정은 하지 않는다.
- 일반 시간·빈도 표현, 알려지지 않은 변수, 손상된 괄호, 같은 피연산자 쌍의 여러 연산, 천 단위 숫자, 괄호 없는 계수 분모는 정규화 대상에서 제외한다. 지원하지 않는 영어 수식 연산어는 기존 재시도로 보낸다.
- Qwen 결과 경로는 **기존 표식 복원 → 연산어 정규화 → 기존 검증**이다. 표식 손상·숫자/기호 유실·함수/분수 방향·용어·존댓말 검사를 유지하며, 남은 times 등 영어 수식 연산어도 검사한다. 최대 2회 생성은 그대로다. 프롬프트·STT·용어집·모델·추론 엔진·API 응답 형식·메모리 제한은 변경하지 않았다.
- `docker/cpu8.defaults`는 CPU 제한·두 스레드를 8로 지정하는 공개 실행 설정이다. 공통 Compose 기본 4 CPU와 `docker/cpu.defaults` 선택지는 유지한다. 현재 서버는 CPU8 설정으로 실행 중이다.

## 실제 실패 출력과 단위 검사

과거 CPU 비교의 출력 119건을 모델 재생성 없이 다시 검사했다. 기존 최종 성공 118건은 계속 통과했고, 과거에 두 시도 모두 실패한 8 CPU 사례도 첫 출력 정규화로 통과했다. 전체 119건이 첫 출력 기준으로 통과했다. 이것은 **저장된 출력의 오프라인 재검사**이며 새 번역 정확도 평가가 아니다.

정규화 뒤에도 잘못된 숫자·반전된 분수·다른 연산·반말은 거부된다. 원문에서 같은 항을 더하고 빼는 두 절의 오역을 정규화로 숨기지 않도록 해당 쌍은 제외한다. 관련 단위 테스트 **80개 통과**: 정규화 경계·HTTP 재시도·Qwen·CPU 구성·테스트 선택기·API 계약·SSE 이벤트·자막 내보내기만 실행했다. 전체 테스트 모음은 실행하지 않았다.

## 같은 19문장의 실제 모델 교차 비교

Mac Apple Silicon RAM 16GB, Linux ARM64 Docker, VM 8 vCPU·6GB 설정을 사용했다. Qwen3-4B-Instruct-2507 Q4_K_M GGUF와 같은 서버 이미지·메모리 4,000,000,000 bytes·GPU 비사용을 유지했다. CPU 제한과 threads·threads-batch를 함께 변경했다.

처음에 실패 문장만 8 CPU에서 3회 실행해 모두 반환됐다. 이어 기존 로켓 묶음 17개와 별도 강의 문장 2개를 **4 → 8 → 8 → 4** 순서로 실행했다. 매 회 같은 캐시 비활성 워밍업 뒤 캐시를 활성화했다. 모델 로딩·워밍업·STT·업로드·자막 시간은 아래 합계에서 제외했다.

| CPU | 첫 실행 | 두 번째 | 평균 | 반환 실패 |
| --- | ---: | ---: | ---: | ---: |
| 4 | 122.156초 | 96.896초 | **109.526초** | 각 0/19 |
| 8 | 117.518초 | 81.235초 | **99.376초** | 각 0/19 |

평균은 약 **9.27%** 짧았지만 실행별 편차가 크다. 고정 순서·각 두 번의 개발 자료 시험으로 안정적인 속도 향상을 확정하지 않는다. 이전 시험의 8 CPU 69.13초와도 실행 시점·처리량이 달라 직접 배수 비교하지 않는다.

각 실행의 생성은 **19회**, 새로 처리한 입력은 **2,119토큰**이었다. 이전 동일 입력 시험은 20회·2,355토큰이었다. 정규화가 재생성을 한 번 줄였고 캐시를 비우는 재시도도 피했다. 출력 토큰은 4 CPU 612개·8 CPU 613개였다. 재시도 상한을 늘리거나 검증을 생략해 성공 처리하지 않았다.

이 시간 측정 뒤 중복 피연산자 쌍·천 단위 숫자의 제외 경계를 보강했다. 실제 생성 79건(문제 문장 3건과 19개 × 4회)을 두 코드로 재검사해 정규화 결과가 전부 동일함을 확인했다. 아래 실제 API 시험은 **보강한 최종 코드**를 사용했다. 측정 당시와 최종 소스를 [별도 해시·원문](math-operator-sources-261025.json)으로 보존했다.

## 최종 코드의 실제 전체 영상 API

원본 `MIT8_01F16_W06PS01-2_360p.mp4` 전체를 `/api/v1/transcriptions?language=en`에 업로드했다. 각 조건에서 backend를 재생성해 STT 미로드를 확인했고, translator는 로드된 상태에서 같은 캐시 비활성 워밍업을 했다. 영상·이미지·STT 설정·17개 영어 묶음·시작/종료 시각은 두 조건에서 일치했다.

| 항목 | 4 CPU | 8 CPU |
| --- | ---: | ---: |
| HTTP 클라이언트 전체 | **133.975초** | **110.264초** |
| 서버 HTTP 로그 | 133.970초 | 110.257초 |
| STT 전체 | 41.923초 | 36.386초 |
| 번역·검증 전체 | 91.894초 | 73.742초 |

| 번역 반환 / 전체 | **17/17** | **17/17** |
| HTTP 상태 | 200 | 200 |

이번 전체 관측은 **23.711초·17.70%** 짧았다. 단, 조건별 한 번이고 4 → 8 순서다. 변경하지 않은 STT도 약 5.54초 차이가 났으므로 전체 감소를 CPU8만의 효과로 귀속하거나 다른 영상의 예상 배수로 사용하지 않는다. 모델 다운로드·Docker 빌드·서버 준비 시간은 포함하지 않는다. 요청 중 STT 로딩·업로드·추론·번역·검증·응답은 포함한다.

문제 문장은 두 조건 모두 첫 생성에서 `... v0 + u × ln(mR / 2m0)입니다.`로 반환됐다. 괄호와 인수는 모델이 생성한 형태를 유지했다. 해당 로그 범위의 원문 불확실성을 해결하거나 수학 정답으로 인증한 것은 아니다. 기존 STT의 u1·불완전한 등식·프라임 해석 문제도 별도 과제로 남는다.

## 현재 실행과 한계

```bash
docker compose --env-file docker/cpu8.defaults up -d --build
```

Windows PowerShell·Mac 터미널에서 같은 명령을 사용한다. Docker에 최소 8 vCPU를 할당해야 한다. 재시작·업데이트에도 같은 env-file 옵션을 사용해야 하며, 4 CPU로 돌아가려면 `docker/cpu.defaults`를 사용한다. CPU8 파일은 CPU 변수 두 개만 바꾸고 메모리·모델·STT·내부 네트워크·GPU 비사용 설정은 같다. 실제 Compose 렌더링에서도 이 차이만 확인했다.

최종 translator는 CPU 제한 8·threads 8·threads-batch 8·device none·GPU layers 0이다. backend·translator healthy, `/health` HTTP 200·두 모델 준비 상태, OOM·재시작 없음도 확인했다. 모델 다운로드·SHA256 검증 경로와 기존 평가 자료는 유지했고 Git 커밋·push하지 않았다.
