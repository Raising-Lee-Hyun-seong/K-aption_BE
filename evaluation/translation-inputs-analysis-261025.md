# 수식 보호·선택적 문맥 구현과 검증

2026-10-25. Qwen3-4B-Instruct-2507 Q4_K_M·CPU·Docker 6GB 설정을 유지하고 번역 입력 준비와 결과 복원만 변경했다. **함수 오류는 해결됐지만 전체 영상의 속도 개선은 검증되지 않았다.**

## 채택한 코드

- `translation_inputs.py`는 발언 안의 지원 수식을 모두 표현할 수 있을 때만 단순 함수·분수·원자 등식을 보호한다. `mr prime equals m of vr`는 `[MATH_A]`로 번역에 전달하고 `mR′ = m(vR)`로 복원한다. 보호 후 다른 기호·연산이 남는 복합 발언은 기존 번역 경로를 사용한다.
- 수식 표식의 개수·정체·순서를 확인하고 원문 수식을 복원한 다음, 보호 전 영어를 기준으로 기존 숫자·변수·함수·분수·용어·존댓말 검증을 모두 적용한다. 누락·복제·변경·순서 역전은 성공으로 처리하지 않는다.
- 명시적인 독립 발언에는 이전 영어 문맥을 생략한다. 지시어·대명사·정정·대조·이어지는 설명은 기존 마지막 256자 문맥을 유지한다. 일반 언어 이해기가 아닌 휴리스틱이다.
- **기존 시스템·사용자 번역 지시를 유지했다.** 지시를 줄이거나 더 적극적으로 문맥을 생략한 후보는 품질이 악화돼 기각했다. 실제 영상 17개 입력 중 프롬프트가 바뀐 것은 인덱스 2·8·10이며, 나머지 14개는 변경 전과 완전히 같음을 확인했다.
- API 영어 원문·시각·응답 형식, STT·묶기·CPU 제한·모델·시도 상한 2회·출력 128토큰·2048토큰 검사는 유지했다. 새로운 추론 서버·외부 API·의존성을 추가하지 않았다.

## 실제 전체 영상: 빨라졌다고 주장할 수 없음

같은 212.586667초 로켓 영상 전체를 실제 작업 API·SSE로 처리했다. 영상 SHA256, STT 영어 원문·시각, 17개 묶음, STT/묶기 코드, 모델 SHA256, translator 이미지·실행 명령, 패키지 버전, VM·컨테이너 CPU/메모리 제한이 일치했다. backend는 후보 코드로 재빌드했고 짧은 확인 호출 뒤 translator를 재시작해 캐시를 초기화했다. 시작 시 STT는 미로드였다.

| 항목 | 기존 Docker 기준 | 채택한 코드 |
| --- | ---: | ---: |
| 전체 | **119.434초** | **137.552초** |
| STT | 28.550초 | 31.774초 |
| 번역 | 90.209초 | 104.723초 |
| 반환 / 실패 | 16 / 1 | **17 / 0** |
| 생성 시도 | 19 | 18 |
| 입력 토큰 합계 | 6,679 | 5,988 |
| 실제 새로 처리한 입력 토큰 합계 | 2,744 | 2,494 |
| 출력 토큰 합계 | 637 | 612 |
| 입력 처리 / 출력 생성 | 64.143 / 25.922초 | 73.418 / 31.051초 |
| SSE·결과·SRT/VTT | 다운로드 성공, 번역 일부 실패 | 모두 성공 |
| OOM·측정 중 컨테이너 재시작 | 없음 | 없음 |

처리량은 줄었지만 이번 전체 실행은 **18.118초, 약 15.2% 더 느렸다.** 변경하지 않은 STT도 느려졌다. 서버의 관측 평균 입력 처리율은 약 42.78 → 33.97 tokens/s, 생성 처리율은 약 24.57 → 19.71 tokens/s였다. 실행 시점의 처리율 변동이 섞여 있지만 CPU 열·클럭·호스트 부하 등 정확한 원인은 분리 측정하지 않았다. 이를 이유로 전체 속도 개선을 추정 확정하지 않는다.

컨테이너 working set 표본 합계의 최대값은 이번에는 약 1.53GB였지만 모델 파일 캐시의 cgroup 귀속·비활성 파일 제외에 영향을 받는 수치다. 모델을 포함한 전체 RAM이 그만큼 줄었다는 증거로 사용하지 않는다. 호스트·VM 전체 최대 메모리는 별도 측정하지 않았다.

## 변경된 세 입력의 교차 비교

전체 실행 결과와 분리해, 같은 Docker CPU 서버에서 **기존 → 후보 → 후보 → 기존(ABBA)** 순서로 인덱스 2·8·10을 재생했다. 수정 전 실제 소스를 별도 프로세스에서 로드했고 해시가 기준 환경과 일치함을 확인했다. API 작업자는 교체하지 않았다. 매 회 같은 문장·문맥의 캐시 비활성 워밍업 후 캐시를 활성화했고 워밍업 시간은 합계에서 제외했다.

| 실행 순서 | 세 입력 번역 시간 | 실패 |
| --- | ---: | ---: |
| 기존 1 | 16.411초 | 1 |
| 후보 1 | 6.939초 | 0 |
| 후보 2 | 5.506초 | 0 |
| 기존 2 | 21.680초 | 1 |
| 평균 | **기존 19.046초 → 후보 6.223초** | **기존 각 1 → 후보 각 0** |

선택한 세 입력에서는 평균 약 **67.3% 감소**했고 함수 관계 실패가 두 번 모두 사라졌다. 이는 저장된 묶음의 번역만 재생한 결과이며 STT·업로드·SSE·자막 시간을 포함하지 않는다. **영상 전체가 67.3% 빨라졌다는 뜻이 아니다.** 구현별 2회씩의 작은 비교로 통계적 속도 개선이나 다른 강의의 일반화를 입증하지 않는다.

## 품질 확인과 남은 한계

- 기존 실패 인덱스 10은 전체 영상에서 첫 시도에 `그리고 그 후에 우리는 mR′ = m(vR)로 갑니다.`로 반환됐다. 함수 이름·인수와 프라임·등식이 보존됐다.
- 인덱스 8의 `mR′ = m0`도 보존됐다. 단순 수식 보호 결과의 표식은 API와 SRT/VTT에 남지 않았다.
- 나머지 복합 수식은 기존 처리를 유지했다. `dvR = u가 상수`라는 불완전한 관계와 STT의 `u1`·적분/로그 범위 불확실성은 남는다. 17개 반환이 의미 정확도 100%를 뜻하지 않는다.
- 별도 선형대수 입력 두 개는 응답됐지만 `쉬습니다` 같은 어색한 문법과 기준 용어 `내적` 대신 `점곱`이라는 동의어가 관측됐다. 독립 전문가 검수·일반 번역 정확도 평가를 수행하지 않았다.
- 지원 기호는 기존 검증기가 다루는 범위다. 일반 수학 파서·STT 오류 복원기·수식 풀이 기능이 아니다. 복잡한 관계는 보호를 강행하지 않는다.
- Windows amd64, 다른 길이의 영상 전체, 호스트 RAM 16GB 예산 준수는 이번에 검증하지 않았다. 모든 실제 모델 시험은 Mac ARM64 Docker다.
