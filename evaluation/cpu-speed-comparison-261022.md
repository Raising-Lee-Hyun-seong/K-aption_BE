# CPU 번역 속도 비교

후속: [2026-10-24 축약형 검증·공통 지시 캐시 최적화](cpu-prefix-optimization-261024.md). 아래 수치는 변경 전의 역사적 기록으로 보존한다.

2026-10-22. `fe23e1a` CPU 통합 커밋 이후의 후속 작업이다. 이 문서와 캐시 최적화 변경은 별도 승인 전까지 커밋하지 않는다.

## 실제 조건

- Apple Silicon Mac의 네이티브 ARM64 Docker, VM 메모리 4,106,604,544 bytes·8 vCPU. VM 메모리는 변경하지 않았다.
- 같은 Qwen3-4B-Instruct-2507 Q4_K_M·고정 CPU 이미지·`--no-repack`·컨텍스트 2048·슬롯 1·CPU 한도 4개를 유지했다. 실제 서버 명령은 각 JSON에 있다.
- 생성 설정·프롬프트·용어집·숫자/수식/존댓말 검증·최대 두 번 재시도는 유지했다. 캐시 조건과 서버 스레드만 비교했다.
- 각 조건에서 같은 별도 문장으로 워밍업한 뒤 짧은 고정 3문장을 한 번 측정했다. 워밍업은 표의 시간에서 제외한다. STT Small CPU INT8 가중치는 비교 프로세스에 유지했으나 오디오 디코딩·STT 추론은 실행하지 않았다.
- fixed는 배경 고정, rolling은 직전 영어 원문을 다음 문맥으로 전달한다. 같은 비교 안에서는 두 캐시 조건의 원문·문맥이 같다. 4스레드는 끔→켬, 2스레드는 켬→끔 순서로 시험했다.

## 관측 결과

| CPU 스레드 | 문맥 | 캐시 끔 합계 | 캐시 켬 합계 | 검증 실패 |
| --- | --- | ---: | ---: | --- |
| 4 | fixed | 19.47초 | 4.25초 | 양쪽 0/3 |
| 2 | fixed | 35.61초 | 7.45초 | 양쪽 0/3 |
| 4 | rolling | 20.87초 | 12.77초 | 양쪽 0/3 |

근거: [4스레드 fixed](cpu-speed-4threads-261022.json), [2스레드 fixed](cpu-speed-2threads-261022.json), [4스레드 rolling](cpu-speed-4threads-rolling-261022.json). 입력·원시 출력·시도별 시간·소스 해시·Docker 표본을 보존한다. 초기 fixed 보고서는 나중에 문맥 모드 라벨만 추가했고 출력·시간은 바꾸지 않았다.

캐시를 끈 4스레드 fixed에서 각 입력의 서버 프롬프트 평가는 약 5.5초·5.5초·7.0초였고 출력 생성은 약 0.28초·0.51초·0.57초였다. 이 짧은 입력에서는 프롬프트 평가가 지배적이었다. 캐시를 켜면 실제 `cache_n`이 fixed에서 248·248·245, rolling에서 248·72·72로 기록됐다. 캐시 요청 플래그만 보고 재사용을 추정한 결과가 아니다.

rolling의 이번 합계 감소는 약 39%다. 첫 사례는 별도 워밍업과 배경이 같아 재사용량이 많았고, 이후 문맥이 바뀐 두 사례에서는 72토큰만 재사용했다. 따라서 이 비율을 전체 강의에 적용하지 않는다. fixed의 큰 개선 폭도 실제 강의 전체의 배수 개선으로 해석하지 않는다. 단일 순차 시험이므로 실행 순서·캐시 상태·열 상태 영향과 통계적 불확실성도 남는다.

4스레드 fixed의 적분 문장은 캐시를 켜면 `우리는`이 추가됐고 나머지 두 문장은 같았다. rolling에서는 세 번역문이 두 조건에서 모두 같았다. 이 3개 사례에서는 검증 실패가 없었지만 일반 의미 정확도나 기존 Q4의 수식·한국어 품질 문제가 해결됐다는 증명은 아니다.

세 비교의 컨테이너 표본 오류·OOM·재시작 증가는 없었다. 컨테이너 working set 합계 관측치는 호스트 전체 RAM이나 7GB 목표 달성 증명이 아니다. Windows 실기기와 6GB VM 비교도 수행하지 않았다.

## 반영한 변경

- 기본 CPU 스레드 4를 유지한다. 이 Mac 시험에서 2로 줄이는 것은 도움이 되지 않았다. Windows 최적값으로 확정하지 않는다.
- 운영 FastAPI 생성자와 Compose에서 `KAPTION_TRANSLATOR_PROMPT_CACHE=true`를 기본값으로 사용한다. `false`로 원래 설정을 선택할 수 있다. true/false 이외 값은 설정 오류로 거부한다.
- 직접 `HttpTranslationService`를 생성하는 통제 평가 경로의 기본값은 false를 유지한다. 과거 Q4/Q8 평가 조건을 임의 변경하지 않는다.
- 기존 메시지·원문 문맥·용어집·생성 설정·검증·재시도와 API 응답 구조를 유지한다. SSE의 선택적 서버 시간 필드는 비교 도구 내부에서만 수집하며 API 응답에 추가하지 않는다.
- `--cache-ram 0`·슬롯 1·컨텍스트 상한은 유지한다. 현재 슬롯의 공통 접두부 재사용은 추가 슬롯 저장용 캐시 RAM과 구분하며 실제 재사용 토큰으로 확인했다.

관련 변경에 연결된 132개 단위 검사를 통과했다. 전체 테스트 탐색은 실행하지 않았다. 기본 캐시를 켠 실제 `POST /api/v1/translations` 경로도 같은 문장 3개·직전 원문 문맥으로 호출해 모두 HTTP 200과 번역문을 확인했다. 실제 backend 환경값도 true였다. [실제 API 결과](cpu-speed-api-smoke-corrected-261022.json)를 보존한다. 초기 시험은 `/api/v1/translate`로 URL을 잘못 입력해 404를 반환했고 [실패 기록](cpu-speed-api-smoke-261022.json)도 보존했다. 이 404를 API 성공 검사에 포함하지 않는다.

## 실제 5분 영상 재측정

같은 MIT 강의 5분 파일로 STT부터 번역·SSE·SRT/VTT 다운로드까지 다시 실행했다. 입력 SHA256은 `e3f54c825fbdfb2b6f6cc486ed5467706601b0cc381dcf72b65df4515f6f08d0`이며, 두 실행의 31개 문장 원문과 시작·종료 시간도 모두 일치한다. 모델 서버가 이미 로딩된 상태에서 시작했고 STT 모델은 작업 중 로딩했다. 이미지 빌드·모델 다운로드 시간은 제외한다.

| 항목 | 이전 5분 실측 | 이번 최종 구성 |
| --- | ---: | ---: |
| 요청부터 결과·자막 확인까지 | 836.73초 (13분 57초) | 814.56초 (13분 35초) |
| 작업 API 내부 처리 | 835.82초 | 813.47초 (13분 33초) |
| STT 전체 | 43.36초 | 47.44초 |
| 번역 전체·검증·재시도 | 792.76초 | 765.94초 (12분 46초) |
| 번역 반환 / 전체 | 27/31 | 27/31 |
| OOM·재시작 증가 | 0 | 0 |

비교에는 동일한 측정 도구의 외부 경과 시간을 사용한다. 전체 감소는 **22.16초·2.65%**로, 짧은 문장 시험의 39%를 재현하지 못했다. 이전 실행 이후 블록 FFT와 프롬프트 캐시가 모두 바뀌었으므로 캐시만의 효과로 귀속하지 않는다. 두 번의 역사적 단일 실행 비교이며 실행 순서·열 상태·메모리 상태 영향도 통제하지 않았다.

이번 실행도 완료 SSE와 SRT/VTT HTTP 200·다운로드 헤더를 확인했다. 다만 4개 구간이 검증에 실패했으므로 `pipeline_succeeded=false`이며, 측정 도구의 종료 코드 1은 이 부분 실패를 반영한다. 원시 결과·시도별 로그·진행 이벤트·메모리 표본·실행 설정은 [이번 5분 결과](cpu-arm64-5min-prompt-cache-261022.json), 비교 대상은 [이전 5분 결과](cpu-arm64-5min-no-repack-261022.json)에 보존한다.

컨테이너 working set 합계의 표본 최대는 3,296,043,008 bytes(약 3.30GB), 컨테이너별 생애 cgroup peak는 backend 1,550,725,120 bytes·translator 2,897,530,880 bytes였다. 개별 최대값은 같은 순간이 아니므로 합산하지 않는다. Docker 관련 호스트 프로세스 physical footprint 관측 합계 최대는 5,111,269,448 bytes였으나 일부 보조 프로세스 측정이 누락돼 전체 RAM·7GB 목표의 검증값으로 쓰지 않는다.

약 4.11GB VM에서 translator의 측정 구간 major fault 증가는 701,263회, `pgscan` 증가는 314,690,775였다. OOM은 없었지만 페이지 회수와 재로딩이 심한 상태였다는 근거다. 파일별 I/O 추적은 수행하지 않아 이 카운터만으로 모델 파일의 반복 읽기량을 확정하지 않는다. VM 6GB와의 속도 비교도 하지 않았다.

실패 구간은 두 실행 모두 23·24·25·30번이며 각각 두 번 `missing_math_symbol`로 거부됐다. 측정 후 읽기 전용 함수 호출로 기존 검증기가 `I'm`의 `m`, `doesn't`·`don't`·`shouldn't`·`haven't`의 `t`를 수식 변수로 잘못 추출하는 결함을 재현했다. 해당 구간에 이 축약형이 포함돼 있다. 이번 작업에서는 코드를 바꾸지 않았고, 영상 측정 도구가 원시 생성문을 저장하지 않으므로 모든 출력의 의미 품질을 판정한 것은 아니다. 다음 수정 대상으로 이 검증 결함을 기록한다.

## 남은 검증

반복 시험·장시간 전체 성공·의미 품질·Windows 실기기·호스트 7GB 목표는 미검증이다. VM 6GB 가설도 이번에 시험하지 않았다. 5분 단일 실측은 수행했지만 전체 번역 성공 판정은 보류한다.
