# Qwen CPU 4·6·8개 비교

2026-10-25. **CPU를 늘리는 것만으로 안정적으로 빨라진다는 결론은 얻지 못했다.** 6 CPU는 전체 입력 두 번의 평균이 약 5.2% 짧았지만 한 번은 4 CPU보다 느렸다. 8 CPU는 가장 빨랐으나 번역 반환 실패가 발생했다. 운영 기본값과 실행 설정을 기존 4 CPU로 복구했다.

## 조건과 측정 범위

- Mac Apple Silicon·호스트 RAM 16GB, Docker Linux ARM64, VM 8 vCPU·6GB 설정(Engine 메모리 6,210,043,904 bytes)이다. Windows amd64는 시험하지 않았다.
- 컨테이너 CPU 제한과 llama.cpp `--threads`·`--threads-batch`를 함께 4·6·8로 바꿨다. 이 세 변수의 효과를 각각 분리한 시험은 아니다.
- Qwen3-4B-Instruct-2507 Q4_K_M GGUF, 같은 서버 이미지, 4,000,000,000 bytes 메모리·RAM+swap 제한, 컨텍스트 2048·슬롯 1·batch 256·ubatch 128·CPU 전용 설정은 유지했다. 서버 실제 명령과 NanoCpus를 매 조건에서 대조했다.
- GPU device none·GPU layers 0·KV/op offload 비활성화가 유지됐다. 모델 SHA256을 시험 후 재확인했으며 공개 명세의 `3605803b982cb64aead44f6c1b2ae36e3acdb41d8e46c8a94c6533bc4c67e597`과 일치했다.
- 현재 운영 번역 서비스와 같은 프롬프트·영어 문맥·용어집·수식 보호·검증·최대 두 번 시도·출력 128토큰·temperature 0·seed 0을 사용했다.
- 클라이언트는 별도 CPU 1개·256MiB 컨테이너에서 기존 backend 이미지로 실행했다. 프로젝트는 읽기 전용 마운트했고 기존 내부 inference 네트워크를 사용했다. 모델 로딩·서버 재생성 시간과 같은 캐시 비활성 워밍업은 번역 합계에서 제외했다. 측정은 캐시 활성화 상태다.
- **저장된 영어 입력의 번역 재생 시간이다. 새 `/api/v1/transcriptions` 전체 처리 시간, STT·업로드·SSE 작업 API·자막 생성 시간으로 해석하지 않는다.**

## 대표 입력 교차 비교

기존 로켓 강의 17개 묶음 중 인덱스 2·10·16과 별도 선형대수 강의 문장 1개, 총 4개를 사용했다. 변수분리·단순 함수·긴 부정/비교 설명·벡터 내적을 포함한다. 순서는 4 → 6 → 8 → 8 → 6 → 4였다.

| CPU·두 스레드 | 첫 실행 | 두 번째 실행 | 평균 | 검증 실패 |
| --- | ---: | ---: | ---: | ---: |
| 4 | 13.939초 | 18.662초 | **16.301초** | 각 0/4 |
| 6 | 12.397초 | 14.084초 | **13.241초** | 각 0/4 |
| 8 | 11.403초 | 11.670초 | **11.536초** | 각 0/4 |

각 조건에서 새로 처리한 입력은 모두 342토큰, 시도는 모두 4회였다. 짧은 비교에서 평균 차이가 5%를 넘어 전체 19개로 확대했다. 이 결과만으로 8 CPU를 채택하지 않았다.

## 전체 19개와 재확인

로켓 강의 묶음 17개와 기존 선형대수 문장 2개를 동일한 원문·문맥·순서로 재생했다. 초기 순서는 6 → 8 → 4였다. 8 CPU에서 실패가 발생해 6 CPU를 재확인했고, 그 시간 변동이 커 마지막으로 4 CPU 기준도 한 번 더 실행했다. 따라서 전체 순서는 **6 → 8 → 4 → 6 → 4**다.

| CPU·두 스레드 | 첫 실행 | 재확인 | 평균 | 번역 반환 실패 |
| --- | ---: | ---: | ---: | ---: |
| 4 | **91.703초** | **89.198초** | **90.450초** | 각 0/19 |
| 6 | **75.755초** | **95.702초** | **85.729초** | 각 0/19 |
| 8 | **69.130초** | 미실행 | 69.130초, 단일 실행 | **1/19** |

6 CPU의 두 번 평균은 4 CPU 평균보다 **4.721초·5.22%** 짧았다. 그러나 6 CPU 자체의 차이는 약 19.947초였고, 두 번째 실행은 두 4 CPU 측정보다 모두 느렸다. 처음 관측한 약 17% 단축을 안정적인 개선으로 확정하지 않는다. 8 CPU를 반복하지 않은 이유는 이미 전체 입력에서 반환 실패가 나타났기 때문이다.

전체 실행 5회에서 새로 처리한 입력 토큰은 매번 **2,355개**, 생성 시도도 매번 **20회**였다. 출력 토큰은 4 CPU 657개, 6 CPU 656개, 8 CPU 654개였다. 4 CPU와 6 CPU는 각각 반복 실행 간 최종 번역문 19개가 모두 일치했다. 단순히 다른 양의 작업을 했기 때문에 6 CPU 시간이 달라진 것은 아니다.

6 CPU의 서버 입력 처리/생성 시간은 첫 실행 **47.364/28.223초**, 재확인 **58.668/36.678초**였다. 입력과 생성 양쪽 처리율이 떨어졌다. 호스트의 다른 앱 활동은 한 시점에 확인했지만, 열·클럭·CPU 배치·호스트 부하·메모리 I/O의 조건별 시계열을 수집하지 않았으므로 정확한 원인으로 귀속하지 않는다.

## 품질과 실패 내용

- 8 CPU의 `rocket-13`은 `v0 plus u ...`와 `... over 2m0` 같은 영어 연산어가 남아 두 시도 모두 `untranslated_math_operator`로 거부됐다. API 계약에 맞는 번역을 반환하지 못했다는 뜻이며, 이를 곧바로 수학 의미 오류율로 환산하지 않는다.
- 같은 입력을 4·6 CPU는 한국어 설명과 `v0`, `u`, `ln(mR / 2m0)` 표현으로 반환했다. 모델·원문·샘플링 설정이 같더라도 스레드 조건별 출력이 달랐음을 관측했다. 내부 수치 원인은 별도로 검증하지 않았다.
- 4·6 CPU 전체 출력은 15/19개가 같았으며 나머지는 연결 표현·서술 방식 등의 차이가 있었다. 6 CPU의 두 실행은 19개 모두 같은 번역을 반환했다.
- 기존 단순 함수 `mR′ = m(vR)`와 `mR′ = m0`는 유지됐다. 별도 선형대수 문장의 스칼라·벡터·내적 표현도 확인했다. 이것은 소수 개발 자료의 검토이며 독립 정확도 평가가 아니다.
- 모든 조건에 기존 `dvr = u가 상수` 같은 불완전한 관계와 불명확한 STT·적분/로그 범위 문제가 남는다. 검증 19개 통과를 의미 정확도 100%로 표시하지 않는다.

## 결정

**운영 기본값은 4 CPU·스레드 4를 유지한다.** 6 CPU는 후보지만 이번 변동 폭 안에서 재현되는 단축을 입증하지 못했다. 8 CPU는 반환 실패 때문에 채택하지 않는다. 이 결과로 CPU 증설의 모든 가능성을 부정하거나 현재 속도를 물리적 한계로 확정하지 않는다.

더 큰 단축을 원하면 다음 비교는 여러 번역 묶음을 한 요청으로 처리하는 방식이다. 요청 횟수·중복 문맥을 실제로 줄이는지, 문장 누락·순서·수식·출력 상한을 유지하는지 따로 검증해야 한다. 이번에 해당 기능을 구현하거나 단축 효과를 측정한 것은 아니다.

## 재현과 검증

- [원시 출력·서버 시간·실제 설정·원문 해시·실행 스크립트·전체 집계](cpu-threads-comparison-261025.json)를 새 파일로 보존했다. 기존 모델 평가·STT·자막 결과를 덮어쓰지 않았다.
- `scripts/evaluate_cpu_translation_threads.py control --directory <새 경로>`로 대표 교차 비교와 최초 전체 비교를 재현할 수 있다. 추가 확인 두 번의 실행 소스는 원시 JSON의 `confirmation_6.source`, `confirmation_4.source`에 보존했다. 자세한 동작은 [DEVELOPMENT.md](../DEVELOPMENT.md)에 있다.
- 실행 중 작업이 있으면 시작하지 않는다. `.env`를 읽지 않도록 공개 기본값 파일을 명시하고 translator만 재생성한다. 이미지·나머지 명령·메모리 제한이 달라지면 중단한다. 정상 종료나 Python 예외에서는 4 CPU로 복구한다. 강제 종료·Docker 자체 장애까지 복구를 보장하지 않는다.
- 실제 모델 시험은 대표 4개 × 6회, 전체 19개 × 5회와 각 워밍업을 실행했다. 관련 단위 테스트 **14개 통과**: 활성 작업 보호·실제 CPU 제한 불일치 거부·예외 시 복구와 테스트 선택기를 검사했다. 전체 테스트 모음은 실행하지 않았다.
- 매 측정 끝의 서버 상태에서 OOM·재시작 증가는 없었다. 컨테이너가 조건마다 재생성되므로 생애 카운터를 서로 빼지 않았다. 메모리 peak·호스트 전체 RAM·CPU throttling 전체 시계열은 이번에 측정하지 않았다.
- 마지막 서버 명령은 CPU 4·threads 4·threads-batch 4로 복구됐고 backend·translator 모두 healthy였다. `/health` HTTP 200과 두 모델 준비 상태를 확인했다. 임시 클라이언트 컨테이너는 제거됐다.
- Compose·모델·STT·운영 번역 로직·API 응답은 변경하지 않았다. 평가 도구·연결된 테스트와 문서만 추가/수정했다. 커밋·push하지 않았다.

원본 영상과 개발용 기준 자막의 출처·불확실성·라이선스는 [로켓 강의](mit_rocket_reference.json)와 [선형대수 강의](holdout-linear-algebra-261021.json)에 보존했다. Windows amd64·5분 전체 API·장시간 동시 요청의 성능은 이번 결과로 검증 완료 처리하지 않는다.
