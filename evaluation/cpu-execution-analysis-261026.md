# STT CPU·소배치와 번역 캐시 후보 비교

2026-10-26. **세 가지 경로를 실제로 시험했지만, 품질을 유지한 추가 속도 개선으로 채택한 후보는 없다.**
운영 STT·번역 프롬프트·CPU 설정은 유지했다. 평가 도구·관련 테스트와 원시 결과를 추가했다.
이번 수치를 배포된 전체 API의 속도 개선으로 해석하지 않는다.

2026-11-03 정리: 미채택 평가 도구와 관련 테스트는 실행 경로에서 제거했다.
아래 도구 설명은 당시 평가의 기록이며 현재 실행 안내가 아니다.
[실험 구현·테스트 원문과 SHA256](retired-experiment-sources-261103.json)에 보존했고,
원시 평가 결과는 기존 파일 그대로 유지했다.

## 환경과 비교 범위

- Apple Silicon Mac, 호스트 RAM 16GB, Linux ARM64 Docker, VM 8 vCPU·6,210,043,904 bytes.
- Whisper Small CPU INT8, beam 5, 영어, VAD, 프로젝트의 메모리 제한 특징 추출기를 사용했다.
- STT 평가 컨테이너는 CPU 제한과 실제 모델 `cpu_threads`를 함께 4 또는 8로 설정했다.
  메모리와 memory+swap 상한은 각각 2,500,000,000 bytes였다. 모델은 기존 캐시에서만 읽었다.
- STT와 Qwen 평가는 겹쳐 실행하지 않았다. 운영 backend와 translator는 유지했다.
- Qwen은 기존 Qwen3-4B-Instruct-2507 Q4_K_M GGUF, CPU 8·threads 8·threads-batch 8,
  기존 메모리·GPU 비사용·검증·입력 상한·개별 번역 최대 2회 시도를 사용했다.
- 원본 영상은 기존 `MIT8_01F16_W06PS01-2_360p.mp4`, 212.5866875초다.
  번역은 기존 로켓 묶음 17개와 이미 검토한 선형대수 문장 2개를 재생했다.
- 새 비공개 평가 세트나 Windows amd64 실기기 시험이 아니다. 호스트 열·클럭·CPU 배치를 통제하지 않았다.

## STT: 8 CPU 증설은 이 환경에서 느렸다

| 조건 | 실제 STT 추론 시간 | 기준 자막 단어 차이 / 369단어 | 판정 |
| --- | ---: | ---: | --- |
| 4 CPU 일반, 초기 1회 | 28.919초 | 51 | 기준 |
| 8 CPU 일반, 1회 | 114.415초 | 51 | 느려서 미채택 |
| 8 CPU 일반 + OpenMP PASSIVE | 120초 컨트롤러 상한으로 중단 | 미측정 | 완료 결과 아님 |

완료한 8 CPU 일반 조건의 원문은 기준과 같았지만 크게 느렸다.
CPU 제한 부족이나 OOM은 관측되지 않았으며, 이 결과만으로 원인을 CPU 종류·발열·스레드 대기로 확정하지 않는다.
PASSIVE 조건의 120초는 시작·로딩·워밍업을 포함한 컨트롤러 상한이므로 순수 STT 시간으로 비교하지 않는다.
OpenMP 대기 정책은 [GNU 문서](https://gcc.gnu.org/onlinedocs/libgomp/OMP_005fWAIT_005fPOLICY.html),
CTranslate2의 스레드 설정은 [공식 문서](https://opennmt.net/CTranslate2/parallel.html)를 참고했다.

초기 8 CPU 배치 2는 수동 중단했다. 해당 exit 137은 OOMKilled=false였으며 OOM 결과가 아니다.
후속 8 CPU 배치 2 + PASSIVE는 기본 타임스탬프 비생성 경로에서 58.671초·단어 차이 52개로 완료했다.
그 다음 반복 조건을 수동 중단해 느린 CPU8 분기의 추가 실행을 제한했다.
완료·시간 초과·수동 중단을 [원시 기록](stt-execution-261026.json)에서 구분했다.

## STT: 소배치는 빨랐지만 자막·전사 품질이 달라졌다

상류 배치 기본값인 `without_timestamps=True`에서는 4 CPU 배치 2가 15.394초였지만,
원시 구간이 39개에서 7개로 줄고 구간이 길어졌다. 기준 자막 단어 차이는 51개에서 52개였다.
이를 기존 자막 동작과 동등한 성공으로 처리하지 않았다.

이어 기존 일반 경로처럼 `without_timestamps=False`를 명시해
**일반 → 배치 2 → 배치 2 → 일반** 순서로 비교했다.

| 조건 | 첫 실행 | 두 번째 실행 | 평균 | 원시 구간 | 기준 자막 단어 차이 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4 CPU 일반 | 27.586초 | 27.663초 | **27.624초** | 각 39 | 각 51 (13.82%) |
| 4 CPU 배치 2 | 16.047초 | 15.972초 | **16.009초** | 각 28 | 각 88 (23.85%) |

추론 시간은 약 42.05% 짧았지만 다음 문제가 생겼다.

- `And then we go to mr prime equals m of vr.` 발언이 빠졌다.
- 마지막 로켓 질량이 이전보다 작아진다는 설명도 빠졌다.
- `rocket sled`가 `rocket's lead`로 바뀌었고 `divide, multiply` 같은 삽입이 생겼다.

모델이 같아도 상류 배치 경로는 이전 텍스트 조건을 비활성화하고 특징을 음성 청크별로 계산한다.
따라서 이것은 동일 알고리즘의 처리량만 바꾼 시험이 아니다.
배치 기능 자체는 [faster-whisper 공식 문서](https://github.com/SYSTRAN/faster-whisper#batched-transcription)에 있다.

마지막 배치 두 실행의 cgroup peak는 각각 1,474,572,288·1,460,199,424 bytes였다.
프로세스 RSS와 전체 컨테이너 메모리는 다른 지표다. 호스트 전체 RAM이나 Windows 16GB의 여유를 검증한 값은 아니다.
모델 로딩·오디오 디코딩·12초 워밍업은 위 추론 시간에서 제외했다.
공식 자막에도 오기가 있어 단어 차이는 의미 정확도 점수가 아니지만, 확인한 발언 누락 때문에 채택하지 않았다.

## 번역 두 문장 묶음: 재처리로 느려졌다

로켓의 고정 개발 사례 8·9·12·13번 네 문장으로
**개별 → 묶음 → 캐시 후보 → 캐시 후보 → 묶음 → 개별** 순서로 시험했다.
두 문장 묶음은 각 입력의 기존 지시·선택 문맥을 전달하고 ID별 두 줄로 출력하도록 했다.
개별 원문 기준으로 표식 복원·정규화·기존 검증을 수행했으며, 거부된 문장만 기존 개별 번역으로 재처리했다.

| 경로 | 첫 실행 | 두 번째 실행 | 평균 |
| --- | ---: | ---: | ---: |
| 기존 개별 번역 | 19.005초 | 17.673초 | **18.339초** |
| 두 문장 묶음 + 실패 문장 개별 처리 | 32.215초 | 34.759초 | **33.487초** |
| 고정 접두부 캐시 후보 | 16.278초 | 16.204초 | **16.241초** |

묶음의 뒤 두 문장은 각각 나눗셈 누락과 미번역 영어 연산어로 거부됐다.
개별 재처리까지 포함하자 약 82.6% 느렸다. 원시 생성·분리 결과·거부 이유·재처리 결과를 보존했다.
묶음의 생성 1회 뒤 각 문장이 기존 최대 2회 재시도를 가질 수 있으므로,
이 원형은 기존 생성 상한과 동등한 운영 구현도 아니다. 운영에 연결하지 않았다.
이 시험은 해당 출력·지시 형식의 원형에 대한 결과이며 모든 배치 방식이 불가능하다는 판정은 아니다.

자료: [네 문장 원시 비교](translation-execution-pilot-261026.json).

## 고정 접두부 캐시 후보: 속도는 줄었지만 문법이 깨졌다

기존 존댓말·수식·번역 지시는 삭제하지 않았다.
변하는 이전 문맥을 사용자 메시지의 별도 영역으로 옮기고,
고정 시스템 지시와 공통 사용자 지시를 먼저 재사용하도록 했다.
참고 문맥과 현재 원문은 각각 이름을 붙여 분리했다.
이는 캐시 범위뿐 아니라 모델이 읽는 메시지 배치도 바꾸므로 출력 품질 검토가 필요했다.

네 문장 시험에서 유망해 전체 19개 입력을 **기존 → 후보 → 후보 → 기존**으로 확대했다.
각 실행은 같은 캐시 비활성 워밍업 후 캐시를 켰다. 모델 로딩·워밍업·STT·HTTP 업로드는 제외했다.

| 경로 | 첫 실행 | 두 번째 실행 | 평균 | 반환 / 전체 | 생성 시도 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 기존 | 61.143초 | 60.222초 | **60.682초** | 각 19/19 | 각 19 |
| 캐시 후보 | 56.356초 | 56.175초 | **56.266초** | 각 19/19 | 각 20 |

평균 4.416초·7.28% 짧았다. 새로 처리한 입력은 실행마다 2,119 → 1,676토큰으로 줄었지만,
생성은 재시도를 포함해 613 → 686토큰으로 늘었다. 입력 비용 감소 일부가 재생성·출력 증가로 상쇄됐다.

문제는 `rocket-3`에서 두 번 모두 다음 문법 오류가 재현된 점이다.

> 그 다음에는 mR에 대한 dmr / mR이 됩니다 합니다.

첫 생성은 반말로 거부됐고, 위 재시도 출력은 기존 문자열 검사를 통과했다.
**19/19 반환은 문법·의미 정확도 100%가 아니다.** 현재 프롬프트보다 품질이 나빠져 미채택했다.
이번에 검증을 완화하거나 잘못된 문장을 기계적으로 잘라 성공 처리하지 않았다.

자료: [전체 19개 원시 출력·시도·실행 소스·집계](translation-execution-full-261026.json).

최종 네 실행은 같은 시각 생성 설정으로 비교했고, 배치의 동일한 단어 차이 88개가 재현됐다.
향후 도구는 import 시 소스를 고정해 이 문제를 피한다.
기존 결과는 덮어쓰지 않았으며 초기 결과도 삭제하지 않았다.
