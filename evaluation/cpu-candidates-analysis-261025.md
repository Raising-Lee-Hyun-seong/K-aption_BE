# CPU STT 옵션·번역 전용 모델 비교

2026-10-25. **이번 후보 중 속도와 수학 번역 품질을 함께 개선했다고 판단할 수 있는 것은 없었다. 운영 기본값을 변경하지 않았다.** STT beam 1은 빨랐지만 자막 대비 차이가 늘었고, M2M100은 훨씬 빨라도 전공 용어·수식·존댓말 품질이 부족했다.

## 환경과 범위

- Mac Apple Silicon, 호스트 RAM 16GB, Docker Linux ARM64, VM 8 vCPU·6,210,043,904 bytes. Windows amd64는 시험하지 않았다.
- 평가 컨테이너는 CPU 4개, RAM 및 RAM+swap 각각 2,500,000,000 bytes로 제한했다. STT와 번역 추론 조건을 동시에 실행하지 않았다. 첫 STT 조건 측정 중 호스트에서 후보 모델을 다운로드하고 평가 이미지를 빌드한 시간은 일부 겹쳤다. 그 영향과 CPU 열·주파수·호스트 부하는 분리 측정하지 않았다.
- 운영 backend·Qwen 서버는 유지했다. Qwen 서버는 기존 별도 4 CPU·4,000,000,000 bytes 제한을 사용했다. 메모리·재시작·이미지 ID는 [집계](cpu-candidates-summary-261025.json)에 보존했다.
- 영상은 기존 `MIT8_01F16_W06PS01-2_360p.mp4`, 212.5866875초다. 원본 해시와 각 조건의 STT 전체 원문을 보존했다.
- 번역은 저장된 동일 STT 묶음 17개와 별도 MIT 선형대수 강의 문장 2개, 총 19개를 재생했다. 후자의 두 문장은 앞선 평가에서 이미 확인한 개발 자료로, 새로운 비공개 평가 세트가 아니다. 한국어 기준 번역은 모델에 보내지 않았다.
- **새 설정의 전체 작업 API·SSE·자막 생성 시간을 측정한 시험이 아니다.** 이전 전체 영상 결과를 대체하거나 Windows 시간으로 해석하지 않는다.

## STT: 빨라졌지만 품질 개선은 확인하지 못함

같은 Small CPU INT8 모델을 재사용하고 오디오를 한 번 디코딩했다. VAD는 유지했다. 모델 로딩·디코딩·업로드·번역을 제외한 STT 시간이다. 순서는 기본 → beam 1 → beam 1+힌트 → beam 5+힌트 → beam 1+힌트 → 기본이다.

| 조건 | 횟수 | 추론 시간 | 공식 자막과의 단어 차이 / WER |
| --- | ---: | ---: | ---: |
| 기본 beam 5 | 2 | 33.007, 28.077초; 평균 **30.542초** | 각 51 / 369, **13.82%** |
| beam 1 | 1 | **16.267초** | 60 / 369, **16.26%** |
| beam 1 + 물리 힌트 | 2 | 21.585, 18.493초; 평균 **20.039초** | 각 57 / 369, **15.45%** |
| beam 5 + 물리 힌트 | 1 | **29.924초** | 60 / 369, **16.26%** |

두 번 실행한 조합은 기본 대비 평균 약 34.4% 빨랐지만 단어 차이는 6개 늘었다. 조합은 `separation of variables`와 일부 프라임 표기를 개선한 대신 기본보다 삽입 수가 1 → 10개로 늘었다. 이것은 발화 오디오를 다시 판정한 정확도 점수가 아니다. 공식 자막에도 오기·수식 표기의 불확실성이 있어 [기준 자료](mit_rocket_reference.json)의 한계를 함께 읽어야 한다.

동일 조건의 두 전사는 재현됐지만 고정 순서·적은 횟수·한 영상만 사용했다. 물리 힌트를 다른 분야 영상에 일반 적용하지 않는다. 조합의 영어·구간 분할이 기본과 달라졌으므로 번역 시간까지 같다고 가정하거나 두 단계의 시간을 합쳐 새 API 처리 시간으로 제시하지 않는다.

원시 결과: [STT 조건별 전체 기록](cpu-candidates-stt-261025.json).

## 번역: M2M100은 빠르지만 채택할 품질이 아님

공개 `facebook/m2m100_418M`의 고정 리비전 `55c2e61bbf05dfb8d7abccdc3fae6fc8512fd636`을 다운로드하고 원본 크기·제공된 LFS SHA256을 확인했다. 기존 호스트 CTranslate2 4.8.2로 INT8 변환하고 Linux ARM64 CTranslate2 4.8.3에서 `device=cpu`, `inter_threads=1`, `intra_threads=4`로 실행했다. 실제 compute type은 `int8_float32`였다. 변환된 모델 디렉터리는 약 499MB이며 다운로드 원본과 구별한다. [원본 모델](https://huggingface.co/facebook/m2m100_418M), [변환 지원 문서](https://opennmt.net/CTranslate2/guides/transformers.html)를 참조한다.

한 조건당 워밍업 1개를 제외한 19개 번역 합계다. Qwen은 기존 문맥·용어 지시·수식 보호·검증·최대 2회 시도를 사용했다. M2M100은 지시문을 처리하는 모델이 아니므로 영어만 입력했고, 결과에는 같은 기존 검증을 적용했다. M2M100에는 이전 문맥·용어 강제·말투 보정·재시도를 추가하지 않았다. **모델 구조만의 통제 실험이나 동등한 기능을 갖춘 완성 서비스 간 비교는 아니다.**

| 조건 | 19개 번역 시간 | 기존 검사 통과 / 거부 |
| --- | ---: | ---: |
| 현재 Qwen Q4 CPU 서비스 | **89.362초** | **19 / 0**; 생성 시도 20회 |
| M2M100 INT8, beam 1, 보호 없음 | **8.107초** | **4 / 15** |
| M2M100 INT8, beam 5 + 기존 수식 보호 | **14.804초** | **5 / 14** |

각 조건 1회, 고정 순서로 측정했으며 일반적 속도 배수나 통계적 성능 보장을 제시하지 않는다. 로켓 17개만의 번역 시간은 각각 86.015·7.409·13.508초였다.

### 실제 오역과 검증기의 한계

- 선형대수 `multiplication by a scalar`를 M2M100 두 조건 모두 `스케일러에 의해 번식`으로 번역했다.
- `dot product ... multiplying two vectors`도 두 조건 모두 `포트 제품`, `벡터를 번식`으로 번역했다.
- **위 두 오역은 기존 휴리스틱 검사를 통과했다.** 따라서 통과 수를 의미 정확도로 사용할 수 없고, 검사 실패만 Qwen으로 보내면 이런 오역이 그대로 남는다.
- 보호+beam 5는 `mR′ = m(vR)`를 보존했지만 다른 사례의 `[MATH_A]`는 버리고 `그러므로 우리는 그분의 은혜를 받았습니다.`를 출력했다. 복원 검사가 이를 `math_placeholder_mismatch`로 거부했다.
- Qwen은 별도 강의의 스칼라 곱을 `스칼라에 의해 곱하는 것은 매우 쉽습니다.`, 내적을 `두 벡터를 곱하여 숫자, 스칼라를 얻는 점곱`으로 번역했다. `점곱`은 `내적`의 다른 표현이며 단순 문자열 불일치만으로 오역 판정하지 않는다.
- Qwen도 기존 `dvr = u가 상수` 관계 혼동과 불분명한 STT 수식에 대한 문제가 남았다. 19개 검사 통과가 의미 정확도 100%를 뜻하지 않는다.

따라서 M2M100을 기본 번역기로 교체하거나 자동 검증 통과 결과를 그대로 배포하는 혼합 경로는 채택하지 않았다.

### 실패 문장만 Qwen으로 보내는 방식의 사후 합산

각 M2M100 조건 시간에, 해당 조건에서 거부된 문장의 이번 Qwen 시간을 더했다.

| 계산 | 합산 시간 |
| --- | ---: |
| beam 1 + 15개 Qwen 재처리 | **91.464초** |
| 보호+beam 5 + 14개 Qwen 재처리 | **95.853초** |
| 처음부터 Qwen | **89.362초** |

이것은 **저장된 개별 측정의 합산이며 실제 혼합 서비스 실행 시간이 아니다.** 캐시·모델 상주·라우팅·동시 메모리 효과를 포함하지 않는다. 그 한계 안에서도 뚜렷한 시간 절감 근거가 없고, 거부되지 않은 오역은 여전히 남는다.

M2M 평가 컨테이너의 프로세스 peak RSS는 약 774MiB와 848MiB, cgroup peak는 약 1.25GiB와 1.30GiB였다. 둘은 다른 지표다. 기존 backend·별도 Qwen 서버·호스트 전체 메모리를 포함하지 않으므로 16GB Windows에서의 총 RAM 검증으로 사용하지 않는다. 각 평가 cgroup의 OOM 카운터와 운영 서비스 재시작은 0이었다.

원시 기록: [Qwen](cpu-candidates-qwen-261025.json), [M2M100 beam 1](cpu-candidates-m2m-beam1-261025.json), [수식 보호+beam 5](cpu-candidates-m2m-protected-beam5-261025.json).

## 결정과 후속 우선순위

1. 운영 STT beam 5·힌트 없음과 기존 Qwen CPU 설정을 유지한다. Compose·모델·API·STT 구현·기존 평가 자료를 변경하지 않았다.
2. 속도 개선보다 먼저 수학 발화의 STT 불확실성과 수식 관계 보존을 분리 평가한다. 문자열·숫자 보존만으로 의미 정확도를 판정하거나 기계적으로 존댓말 어미를 붙이지 않는다.
3. 추가 최적화는 Qwen CPU 스레드·배치 설정을 같은 입력의 교차 순서로 비교하는 것이 다음 범위다. 이번에 6·8 스레드나 다른 모델의 성능까지 검증한 것은 아니다. Qwen을 사용하는 문장 수와 생성량을 실제로 줄이지 못한 혼합 구성은 도입하지 않는다.

## 재현·감사 자료

- 평가 전용 `scripts/evaluate_cpu_stt_options.py`, `scripts/evaluate_cpu_translation_models.py`, `docker/Dockerfile.translation-eval`을 추가했다. 운영 Compose는 이 Dockerfile을 사용하지 않는다.
- STT 컨테이너는 운영 backend 이미지, 프로젝트 읽기 전용 마운트, 기존 Whisper 캐시, 네트워크 차단으로 실행했다. 번역 후보도 프로젝트·변환 모델을 읽기 전용 마운트하고 외부 네트워크를 차단했다. Qwen 재생 컨테이너만 기존 내부 inference 네트워크를 사용했다.
- [원본 모델 파일·공개 해시](cpu-candidates-model-261025.json), [변환 모델 해시·환경·집계](cpu-candidates-summary-261025.json), [실제 실행한 스크립트 원문·해시](cpu-candidates-drivers-261025.json)를 보존했다.
- 최초 실행 스크립트가 기록한 Qwen JSON의 `beam=1`, `math_protection=false`는 M2M용 CLI 인자 기본값으로 Qwen 실행에는 적용되지 않았다. 실제 Qwen은 기존 서비스의 샘플링과 수식 보호를 사용했다. 실행 뒤 스크립트의 **표시 메타데이터만** Qwen에 맞게 수정했다. 원시 결과와 당시 소스를 보존했으며 생성 로직·측정 결과를 바꾸지 않았다.
- 실제 Docker 시험은 STT 추론 6회와 번역 3조건 각 19개·워밍업을 실행했다. 이는 운영 전체 API 회귀 테스트를 새로 수행했다는 의미가 아니다. 전체 단위 테스트 모음은 실행하지 않았다.
- 임시 평가 컨테이너는 실행 후 제거했고 운영 두 서비스는 healthy로 유지했다. 평가용 이미지·다운로드/변환 모델은 로컬 임시 경로에 남겼으며 Git에 모델 파일을 추가하지 않았다. 커밋·push하지 않았다.
