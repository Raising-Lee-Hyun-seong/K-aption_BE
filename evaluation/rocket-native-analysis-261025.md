# 프로젝트 로켓 영상 전체 실행·속도·품질 분석

2026-10-25. 프로젝트의 `MIT8_01F16_W06PS01-2_360p.mp4` **전체 212.586667초(3분 32.59초), 21,729,088 bytes**를 실제 API로 처리했다. 이전에 전 구간 실패한 요청과 파일 크기·길이가 일치한다. 이전 업로드의 SHA256은 없어 동일 파일의 바이트 일치까지 확정하지는 않는다.

## 환경과 측정 범위

- Apple Silicon ARM64 Mac, 물리 RAM 16GiB, OS가 보고한 CPU 10개. Qwen3-4B-Instruct-2507 Q4_K_M GGUF와 Whisper Small CPU INT8. 모델 크기·SHA256은 고정 명세와 일치했다.
- Docker 엔진에 연결되지 않아 기존 CPU 전용 llama.cpp 네이티브 빌드 `339f3242c761f16c27e5ffcde1d35dcc31933a55`를 사용했다. Metal·CUDA·Vulkan 빌드 옵션 OFF, device none·GPU layers 0·KV/연산 오프로딩 OFF다. **Docker 6GB·Windows amd64 측정이 아니다.**
- 번역 threads / threads-batch 4, context 2048, parallel 1, batch 256, ubatch 128, cache RAM 0, no-repack, prompt cache true. STT beam 5·VAD true, OpenMP 4를 사용했다. 네이티브 프로세스에 Docker의 CPU·메모리 제한은 적용되지 않는다.
- 현재 작업 트리의 수식 결합·검증 변경을 포함한 코드를 실행했다. 이전 Docker 이미지에서 얻은 167초 또는 60초 음성 결과와 통제된 전후 비교가 아니다.
- 준비된 모델의 서버 시작 시간·파일 무결성 검사 시간은 전체 처리 시간에서 제외한다. 최초 STT 로딩은 포함한다. 단일 전체 실행이므로 반복 실행 분산은 확인하지 않았다. 호스트 최대 메모리·swap은 별도 측정하지 않았다.
- 격리 포트 18000/18080과 별도 작업 폴더에서 `POST /api/v1/jobs`를 실행했다. 동기 `/api/v1/transcriptions`와 같은 처리 함수를 사용하지만 동기 엔드포인트 자체의 시간은 아니다.
- 관측용 래퍼가 원래 STT·생성 결과를 변경하지 않고 원시 후보·서버 시간·로그를 기록했다. 파일 기록 비용은 측정 시간에 포함된다. 소스 해시·패키지 버전·평가 코드도 보존했다.

## STT 옵션 실제 비교

같은 CPU 모델을 재사용하고 오디오를 한 번 디코딩한 뒤 기본 → beam 1 → 물리 힌트 순서로 각 1회 추론했다. **아래 시간은 STT 추론만이며 전체 API 시간이 아니다.**

| 옵션 | 추론 시간 | STT 조각 | 공식 자막 대비 단어 오류 / 기준 369단어 |
| --- | ---: | ---: | ---: |
| 기본 beam 5 | 19.310초 | 45 | 57개, 15.45% |
| beam 1 | **12.532초** | 49 | 57개, 15.45% |
| beam 5 + 물리 문맥·용어 힌트 | 20.227초 | 42 | **50개, 13.55%** |

beam 1은 이 실행의 STT 추론에서 약 **35.1%, 6.779초 단축**됐다. 다만 문구·구간 경계가 달라졌고 이후 문장 묶기·번역 비용도 바뀔 수 있다. 전체 API가 6.779초 빨라졌다고 검증한 것은 아니다. 모델 재사용 상태·고정 실행 순서의 영향을 배제하지 못한다.

힌트는 `rocket's lead`를 `rocket sled`로, `separation variables`를 `separation of variables`로 개선했다. 함수 인수와 `u1`, `2 vR prime` 같은 수식의 불확실성은 남았다. 이 강의의 분야에 맞춰 선정한 힌트이며 독립 영상의 개선을 증명하지 않는다. **beam 1과 힌트를 동시에 쓴 조건은 시험하지 않았다.**

공식 자막에는 `arrived/derived`, `2/to`, 수식 띄어쓰기·기호의 불확실성이 있다. 위 오류율은 철자 기반 비교 지표이고 음성 인식의 실제 정확도나 번역 정확도가 아니다. [faster-whisper 공식 문서](https://github.com/SYSTRAN/faster-whisper)는 속도 비교 시 탐색 폭과 단어 오류율을 함께 비교하도록 안내한다. 힌트 옵션은 [공식 전사 구현](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/transcribe.py)에도 정의되어 있다.

## 프롬프트 후보 실제 비교와 기각

입력 처리가 병목이므로 반복되는 연산어 지시를 사용자 메시지에서 고정 시스템 접두부로 옮긴 후보를 별도로 시험했다. 현재 원문의 인덱스 2·6·16·21, 같은 문맥·4 threads·캐시·워밍업을 사용했다.

| 네 구간 한 번 비교 | 현재 지시 | 접두부 이동 후보 |
| --- | ---: | ---: |
| 시간 | 20.575초 | 22.033초 |
| 실패 구간 | 2 | 3 |
| 시도 횟수 | 6 | 7 |
| 새로 처리한 입력 토큰 | 882 | 823 |
| 생성 토큰 | 140 | 172 |

새 입력 토큰은 줄었지만 정상 등식 구간에서 외국 문자 혼입이 새로 발생해 재시도가 늘었다. **후보는 채택하지 않았다.** 현재 고정 접두부 캐시는 이미 켜져 있다. 지시를 앞에 옮기거나 입력 토큰을 줄였다는 이유만으로 실제 시간·품질 개선을 주장할 수 없다.

## 정확도에서 확인된 문제

전체 결과의 다음 대표 구간을 직접 검토했다. 독립 전문가의 정답률 평가는 수행하지 않았다.

| API 인덱스·시간 | 문제 | 개선 방향 |
| --- | --- | --- |
| 1 · 7.28초 | STT의 `rocket's lead`가 번역에서도 로켓 앞쪽으로 이어짐 | STT 단계부터 물리 용어 힌트 적용 후보 검증 |
| 8 · 47.00초 | 앞 문맥의 m 이동 설명을 덧붙이고 `dvR = u가 상수`로 옮김. 현재 검증은 통과 | 현재 발언과 문맥의 경계, 등식의 인자·관계와 이전 문장 복사 검사 보완 |
| 13 · 76.40초 | 불명확한 `2 vR prime of t`를 `2vR' of t`로 반환 | 프라임·함수 표현 보존과 미번역 검증. 원음이 불명확하면 임의 정답식으로 보정하지 않음 |
| 14 · 94.12초 | `mR prime equals m0`를 `mR'이 m0에 등록됩니다`로 반환 | equals와 등식 관계 검증·표현 보존 강화 |
| 16 · 116.40초 | `m of vR`를 두 번 모두 `m의 vR`로 뒤집음 | 함수 이름·인수 구조를 보존하는 변환과 실패 사유별 재시도 실험 |
| 18 · 127.40초 | 영어 연산어를 남기거나 재시도에서 나눗셈을 잃어 실패 | 분수·등식 관계를 함께 보존. 애매한 u1을 임의로 적분 기호로 바꾸지 않음 |
| 21 · 156.89초 | 두 시도 모두 plus·over를 그대로 남겨 실패 | 수식 표현을 보호하고 한국어 설명을 생성하는 방식 비교 |

일반 문장과 마지막 감속·정지 설명은 대체로 전달되지만, **반환 성공한 문장에도 문맥 혼입·수식 오역이 남아 있어 강의 자막을 그대로 신뢰할 단계는 아니다.** 검증을 약하게 바꿔 실패 수만 줄이면 잘못된 수식이 반환될 수 있다.

## 다음 작업 우선순위

1. **번역 입력 처리 최적화**: 가장 큰 69초 구간이다. 고정 지시의 중복·불필요한 문맥을 줄이는 후보를 실제 강의와 별도 강의에서 비교한다. 고정 접두부 재배치 후보는 이번에 기각했다. 더 긴 자막을 무조건 합치거나 재시도를 끄는 변경은 품질 저하를 함께 측정해야 한다.
2. **STT 빠른 옵션 검증**: beam 1은 단일 STT 비교에서 개선됐다. 전체 API로 구간 묶기·수식 실패까지 다시 비교한 뒤 빠른 옵션 채택을 판단한다. 분야 힌트는 정확도 후보이며 beam 1과의 조합은 추가 시험 대상이다.
3. **수식 보존과 재시도 개선**: 인식이 확실한 기호·함수·등식·분수를 구조로 보호하고 모델은 주변 한국어 설명을 만들게 하는 후보를 비교한다. 임의의 적분을 풀거나 애매한 STT를 정답식으로 덮어쓰지 않는다. 현재 재시도는 주로 문맥 제거·존댓말 재지시여서 같은 함수 오류를 반복하므로 실패 사유에 맞는 짧은 교정 지시를 시험한다. 15.6초는 재시도를 없애면 자동으로 얻는 안전한 단축량이 아니다.
4. **목표 Windows에서 CPU 설정 비교**: 입력 처리와 생성을 나눠 threads / threads-batch 4·6·8을 비교한다. VM vCPU와 컨테이너 CPU 제한도 함께 확인해야 한다. 이번 Mac의 최적 스레드 수·Windows 성능은 측정하지 않았다. [llama.cpp 공식 성능 도구](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md)는 입력 처리·생성·스레드별 반복 측정을 지원한다.

모델·운영 프롬프트·STT 기본값을 이번 분석에서 바꾸지 않았다. 기존 작업 트리 변경과 평가 결과를 유지했고 커밋·push하지 않았다. 추가 단위 테스트나 전체 테스트 모음은 실행하지 않고 요청한 영상·옵션 평가만 수행했다.
