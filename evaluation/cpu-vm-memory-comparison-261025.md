# Docker VM 메모리 4GB·6GB 실제 비교

2026-10-25, Apple Silicon Mac ARM64 / 물리 RAM 16GiB. Docker Desktop 메모리를 4096MiB에서 6144MiB로 변경했다. 실제 Engine 메모리는 각각 4,106,604,544 / 6,210,043,904 bytes로 확인했다. 테스트 후 **6144MiB 설정과 기존 두 서비스를 유지**했다.

관측상 전체 시간은 **0.993초, 약 2.99% 감소**했다. 번역은 약 5.77% 빨라졌지만 STT는 약간 느려졌다. 원문·시각·한국어 출력 전체가 두 조건에서 동일했다. 두 실행 모두 SSE 완료, 결과 조회, SRT·VTT 다운로드 HTTP 200과 다운로드 헤더를 확인했다. 표본 수집 오류·컨테이너 OOM·실행 중 재시작은 없었다.

6GB에서 메모리 회수와 번역 컨테이너 major page fault가 감소한 것은 메모리 압박 완화와 일치한다. 다만 major page fault만으로 특정 모델 파일의 재독출 횟수나 디스크 대기 시간을 확정하지는 않는다. **각 조건 1회 측정이므로 약 3% 차이를 지속적인 속도 개선으로 단정할 수 없다.** 이번 입력에서는 메모리 증설만으로 큰 처리 시간 감소가 관측되지는 않았다.

## 비교 조건과 범위

- 기존 MIT 18.02 강의 5분 평가 자료의 첫 60초 음성을 stream copy로 추출했다. 파일 길이 60.000998초, 디코딩 길이 60.00075초다. 사용자가 제공한 로켓 영상이나 5분 전체 영상의 처리 시간이 아니다. 원본 출처는 [기존 미디어 출처 기록](cpu-long-media-provenance-261022.json)에 있다.
- 입력 SHA256: `d88a441fa189c34d46455fa032dde024551e6ae0c21f598b0e3967c89ecab69d`.
- 4GB 측정 전에도 Docker Desktop을 재시작했고, 6GB 변경 후에도 재시작했다. 두 조건 모두 Qwen 로드 완료·STT 미로드 상태에서 작업을 시작했다. Qwen 시작 시 모델 로딩은 시간에서 제외하고 STT 모델 로딩은 포함한다.
- 두 조건에서 같은 기존 컨테이너·이미지·실행 명령·소스 해시를 사용했다. VM CPU 8개, 각 컨테이너 CPU 제한 4개, backend 메모리 제한 2,500,000,000 bytes, translator 제한 4,000,000,000 bytes를 유지했다. 설정 파일에서는 메모리 숫자만 변경했고 CPU·swap 설정은 유지했다.
- 모델은 현재 실행 중인 **Qwen3-4B-Instruct-2507 Q4_K_M GGUF CPU** 구성이다. 작업 트리의 미커밋 수식 처리 변경은 이미지에 반영하지 않았다. 기존 실행 환경의 RAM 차이만 비교했으며 모델·추론 설정은 바꾸지 않았다.
- `POST /api/v1/jobs`로 접수해 SSE·결과·자막까지 확인했다. 공통 STT·번역 파이프라인을 실행한 시간이며 동기 `/api/v1/transcriptions` 엔드포인트 자체의 직접 측정은 아니다. 외부 시간에는 약 1초 간격 상태 알림의 영향이 있다.
- 4GB 다음 6GB 순서로 각 1회 실행했다. macOS 파일 캐시·호스트 부하·실행 순서를 통제하지 않았다. 긴 영상의 메모리 압박이나 반복 요청 성능을 대표하지 않는다.
- 메모리는 주기적으로 수집한 컨테이너 working set이며 VM·호스트 오버헤드와 짧은 피크는 포함하지 않는다. 호스트 RAM·swap 사용량을 별도 계측하지 않아 16GB 전체 메모리 예산 충족 여부는 검증하지 않았다. 제공되지 않는 swap·refault 카운터는 JSON에서 `null`로 유지했다.
- 전체 번역 반환은 의미 정확도 검증을 뜻하지 않는다. Windows amd64 실기기는 테스트하지 않았다. 코드 수정·이미지 재빌드·커밋·push는 이번 RAM 테스트에서 수행하지 않았다.
